# 省 Token 工作流

## 核心原则

让 AI 生成**数据**，让脚本生成**重复结构**。不要让 AI 为 100–200 个场景分别编写 `<tr>`、样式、按钮或百分比条。

## 必须遵守

1. 复用 `assets/probability-page-template.html`，不要在每次任务中重写 CSS 和 JavaScript。
2. 使用 `references/web-mode.md` 的七字段数组，不使用重复长键名的对象数组。
3. 把场景直接写入本地 JSON，不在回复中输出完整 JSON、HTML、CSS 或 JavaScript。
4. 调用 `scripts/build_probability_page.py` 完成排序、校验、HTML 转义、数据注入和百分比条渲染。
5. 最终回复只报告成品路径、事件名、条目数和验证结果，不重复页面里的 100–200 条内容。
6. 修改功能时修改一次模板；修改单个事件时只替换数据文件。

## 上下文管理

- 构建时让脚本读取模板，不要为了每次生成都把模板完整读入对话。
- 只有需要改变交互或视觉时才读取模板的相关片段。
- 按主题分批构思场景，每批约 25–40 条；写入后只保留批次摘要和去重结论，不在后续消息重复前文。
- 先列机制，再写数据，避免边写边重复解释概率方法。
- 使用脚本报告重复项、非法字段和数量问题，只修复报错条目。
- 不创建额外的说明文档、截图或多份相同 HTML，除非用户明确要求。

## 内容与 Token 的平衡

- 每条事件、依据和建议尽量控制为一个短句，但不得牺牲关键条件。
- 概率使用粗粒度数字，证据把握仅保留高、中、低。
- 合并近乎相同的场景，不通过无意义变体凑到 100 条。
- 对共同条件使用 `assumptions` 统一说明，避免每行重复相同背景。
- 对真正不同的条件变体保留条件短语，例如“若次日需要驾驶”，不能为了省字删除条件。

## 交付检查

若回复正在包含大段重复标签或完整数据列表，停止并改为“写 JSON → 运行构建脚本 → 交付 HTML 文件”。页面文件可以很大，但对话上下文不需要承载其重复结构。
